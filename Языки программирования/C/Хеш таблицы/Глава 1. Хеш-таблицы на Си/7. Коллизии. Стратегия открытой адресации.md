Смысл открытой адресации (open addressing) в том, чтобы хранить все элементы непосредственно в массиве самой хеш-таблицы, как и при прямой адресации, не создавая дополнительных структур вроде связных списков. Как и в общем случае, вычисляется индекс для вставки данных (например, путем получения остатка от деления хеша на размер таблицы). Однако если есть коллизии и нужный индекс уже используется, то для хранения значения надо найти другую свободную ячейку. Такой поиск еще называют "зондированием" (probing).

Подобный подход позволяет сэкономить память, так как не нужно тратить ресурсы на указатели и узлы списков. Кроме того, обеспечивается сравнительно высокая скорость (Cache locality): поскольку все данные лежат в памяти рядом (в одном массиве), процессор обрабатывает их быстрее, чем "прыгая" по ссылкам в разные части памяти.

Основной минус: в отличие от стратегии со связанными списками при открытой адресации в таблице может кончиться место для новых ключей. Поэтому необходимо иметь стратегию на случай заполнения таблицы на 100%. Обычно при заполнении на 70-80% ее приходится расширять. Кроме того, чем больше таблица забита, тем дольше длится поиск свободной ячейки.

### Стратегии зондирования

Ключевая проблема при открытой адресации заключается в поиске незанятых ячеек, куда можно вставить новые данные, или то, что называется стратегией зондирования. Распространены следующие три стратегии:

-   Линейное зондирование (linear probing): если место i занято, проверяем i+1, затем i+2 и так далее, пока не найдем пустое место.
-   Квадратичное зондирование: расстояние между проверками увеличивается квадратично (1, 4, 9...), что помогает избежать скопления элементов в одном месте.
-   Двойное хеширование (double hashing): интервал поиска определяет вторая хеш-функция.

Стратегию зондирования можно выразить функцией `p(k, i)`, которая возвращает индекс и которая зависит от хеш-ключа k и индекса i (который изменяется от 0 до m - 1, где m обозначает размер хеш-таблицы). При вставке в таблицу хеш-значения k сначала мы пытаемся добавить его по индексу `p(k, 0)`. Если этот слот занят, то вместо этого мы пытаемся использовать `p(k, 1)`. Если же и этот слот тоже занят, то переходим к `p(k, 2)` и так далее. В итоге мы проверяем последовательность `p(k, 0), p(k, 1), p(k, 2), ..., p(k, m-1)`. Таким образом, если вся таблица еще не заполнена, то мы так или иначе найдем пустое место для размещения данных.

Рассмотрим в обшем виде пару стратегий.

#### Линейное зондирование (linear probing)

Линейное зондирование (linear probing) представляет самую простую в реализации стратегию. Она подразумевает линейный поиск от индекса, чтобы добраться от ключа до конца таблицы, а затем переход к началу таблицы. Такая стратегия выражается формулой:

p(key, index) = (key + index) mod size

Общий процесс вставки ключа выглядит следующим образом:

1. Вычисляется индекс: p = (key + 0) % size.
2. Если ячейка p занята, проверяем `p + 1` или (`(key + 1) % size`) .
3. Если и она занята - проверяем p + 2, и так далее по кругу, пока не найдется пустая ячейка.
4. При поиске алгоритм точно так же идет по цепочке, пока не найдет нужный ключ или пустую ячейку (что означает, что ключа нет).

Главный минус подобной стратегии - так называемая первичная кластеризация (Primary Clustering). Она заключается в том, что занятые ячейки имеют свойство группироваться в длинные блоки. Чем длиннее такой "кластер", тем больше проверок приходится делать, что замедляет работу таблицы до линейного времени O(n).

При этом надо учитывать, что последовательности для разных ключей могут накладываться друг на друга. Например, возьмем, что для ключа k1 индекс будет равен P1, но, допустим он занят. Тогда при наличии сводобных ячеек мы можем найти некий индекс Pn и в его ячейку поместить ключ. Но пусть у нас также будет второй ключ k2, базовый индекс которого равен P2 и находится между P1 и Pn - `[P1...P2...Pn]`. Поскольку все ячейки вплоть для Pn заняты, то для ключа k2 выбираем индекс P(n+1).

Таким образом, ключ страдает от коллизий ключа, хотя их изначальные индексы были разными. Чем длиннее такой общий кластер, тем больше шагов (проб) нужно сделать как для вставки, так и для поиска

Но перейдем к коду. Предположим, что размер таблиц представляет степень двойки, а это значит, что можено заменить операцию получения остатка на маскирование и реализовать зондирование следующим образом:

```c
unsigned int p(unsigned int key, unsigned int index, unsigned int size)
{
    return (key + index) & (size - 1);
}
```

#### Двойное хеширование

Двойное хеширование (double hashing) предполагает использование двух разных хеш-функций: одна сопоставляет ключ с начальным индексом, а другая определяет последовательность зондирования. Двойное хеширование выражается через следующую формулу:

p(key, ind) = (hash_func_1(key) + ind * hash_func_2(key)) mod size

Где `key` - ключ, `hash_func_1` и `hash_func_2` - функции хеширования, `ind` - начальный индекс, `size` - количество ячеек таблицы.

Смысл двойного хеширования состоит в том, чтобы при поиске свободной ячейки сделать шаг ("прыжок"), который будет индивидуальным для каждого ключа. В формуле выше подвыражение `hash_func_2(key)` по сути и представляет шаг. В линейном пробировании шаг всегда равен 1 (или константе). Из-за этого все ключи, попавшие в одну область, выстраиваются в одну длинную очередь (кластер). Двойное хеширование разбивает эти очереди.

Таким образом, даже если у двух разных ключей k_1 и k_2 совпал основной индекс (`hash_func_1(key)`), их вторые хеш-функции (`hash_func_2(key)`) почти наверняка выдадут разные значения шага. В итоге они не "слипаются" в один кластер, а разлетаются по разным частям таблицы. Это полностью решает проблему первичной кластеризации.

На данный момент можно предположить, что ключи уже являются хеш-ключами и, следовательно, `hash_func_1` будет тождественной функцией (identity function), то есть `key = hash_func_1(key)`. Поэтому основная задача состоит в подборе второй функции - `hash_func_2`. Чтобы она работала эффективно, она должна отвечать двум главным критериям:

-   Никогда не должна возвращать 0 (иначе шаг будет нулевым, и мы зациклимся на одной ячейке)
-   Результат `hash_func_2(key)` должен быть взаимно прост с размером таблицы size (То есть наибольший общий делитель `hash_func_2(key)` и размера таблицы равен 1). Это гарантирует, что в процессе прыжков мы со временем посетим все ячейки таблицы, а не будем ходить по кругу в узком цикле.

Кроме того, эта функция не должна быть просто модификацией первой функции хеширования или зависеть от нее (например, `hash_func_1(key) \ 2`), иначе распределение останется похожим, и мы снова получим кластеризацию. И также в идеале она должна вычисляться быстро, так как при высокой нагрузке на таблицу ее придется считать часто.

Самые популярные способы определения функции:

-   Если размер таблицы - простое число

    В этом случае вторую функцию можно вычислять по формуле `hash_func_2(key) = R - (key mod R)`, где `R` - простое число, чуть меньшее, чем размер таблицы.

    Вычитание из `R` гарантирует, что результат будет в диапазоне `[1, R]`, то есть никогда не будет равен 0. Так как размер таблицы представляет простое число, то любое число `hash_func_2(key) < size` будет взаимно простым с size.

-   Если размер таблицы - степень двойки (например, 1024, 2048)

    В этом случае `hash_func_2(key)` должна всегда возвращать нечетное число, потому что любое нечетное число будет взаимно простым со степенью двойки

    Пример реализации: `hash_func_2(key) = (2 * any_hash_func(key) + 1) mod size`. Прибавление единицы к четному числу всегда дает нечетный "шаг".

В итоге, двойное хеширование дает почти идеальное распределение, но оно чуть медленнее линейного пробирования из-за вычисления второго хеша и промахов мимо кэша процессора (прыжки по памяти хаотичны).

Пусть для размера хеш-таблиц используется степень двойки, тогда подойдет любая хеш-функция, которая возвращает нечетные числа. Поэтому простой подход заключается в преобразовании ключа в нечетное число путем сдвига битов на одну позицию и установки младшего значащего бита в 1:

```c
unsigned int p(unsigned int key, unsigned int i, unsigned int m)
{
    unsigned int h1 = key;
    unsigned int h2 = (key << 1) | 1;
    return (h1 + i*h2) & (m - 1);
}
```

### Последовательность зондирования

Одним из ключевых аспектов в открытой адресации является последовательность зондирования (probing sequence). Это список ячеек хеш-таблицы, по которым проходим в поисках свободного места, если при вставке данных возникла коллизия. При поиске элемента в таблице нужно пройти по той же самой последовательности, иначе данные не найти. То есть фактически это маршрут, по которому алгоритм обходит ячейки таблицы.

Например, при алгоритм линейного зондирования обходит все ячейки подряд. Если для некоторого ключа key мы получили индекс P1, но он занят, тогда алгоритм идет дальше и наконец доходит до некоторого индекса Pn, ячейка по которому не занята и которая будет использоваться для хранения ключа. В итоге получаем последовательность занятых ячеек P1...Pn, в пределах которой алгоритм будет искать ключ key (в идеале).

В стандартных условиях поиск в последовательности зондирования прекращается в трех случаях:

-   Ключ найден: мы начали искать ключ key начиная с индекса P1 и наконец нашли ячейку с индексом Pn, где лежит именно то, что мы искали. Успех.
-   Найдена пустая ячейка: это критически важный момент. Если алгоритм встречает абсолютно пустую ячейку (которая никогда не была занята), он останавливается. Логика проста: если бы ключ был в таблице, он бы занял это место при вставке или ушел бы по цепочке дальше. Раз здесь пусто - ключа в таблице нет.
-   Круг замкнулся: алгоритм проверил все ячейки таблицы и вернулся в начало. Это значит, что таблица полностью заполнена и ключа в ней нет.

### Стратегии удаления

Как было указано выше, если алгоритм при проходе по последовательности зондирования встречает абсолютно пустую ячейку (которая никогда не была занята), он останавливается. Поэтому при зондировании нельзя просто удалить элемент, оставив пустую ячейку. Если вы это сделаете, цепочка поиска для других элементов, которые были вставлены после удаляемого, разорвется. Поиск дойдет до пустой ячейки и решит, что искомого ключа в таблице нет, хотя он просто лежит дальше.

Для решения проблемы удаления используют два основных метода:

-   Ленивое удаление (Tombstones): вместо того чтобы очистить ячейку, ее просто помечают как удаленную (название стратегии связано с тем, что для удаления применяется специальный маркер или флаг, который еще назвают "надгробие" или по английски "tombstone"). Здесь можно отметить следующие аспекты:

    -   Поиск: если алгоритм встречает маркер, который указывает на удаление, он не останавливается, а продолжает искать дальше.
    -   Вставка: новые элементы могут записываться поверх ранее записанный (при условии, если они网店ены как удаленные), что позволяет повторно использовать память.
    -   Минус: если удалений много, поиск может занять много времени (придется просматривать много "надгробий" перед тем, как найти элемент или реально пустую ячейку). Проблема решается полной перестройкой таблицы (rehash), когда количество помеченных ячеек становится критическим.

-   Рехеширование кластера (Backshift Removal): это более сложный, но в то же время более "чистый" способ без использования маркеров, который выглядит следующим образом:

    -   Удаляем нужный элемент.
    -   Проверяем следующую ячейку. Если она пуста - работа закончена.
    -   Если она занята, нужно проверить, не должен ли элемент в ней (назовем его X) переместиться назад на освободившееся место.
    -   Если "родной" индекс элемента X находится до или на месте только что освобожденной ячейки, сдвигаем X назад, а текущую позицию X помечаем как свободную.
    -   Повторяем процесс для следующей ячейки, пока не встретим пустоту.

    Это позволяет сохранить структуру кластера плотной и исключает дыры и использование всяких маркеров.

### Реализация

Реализацию этой стратегии начнем с определения структуры корзины хеш-таблицы:

```c
struct bin 
{
    unsigned int key;
    int in_probe : 1;   // корзина - часть последовательности использованных корзин
    int is_empty : 1;   // корзина пуста (но может быть частью последовательности использованных корзин)
};
```

Здесь флаг `in_probe` может принимать одно из двух значений: 1 или 0 (по сути true или false). Зачем этот флаг нужен? С помощью этого флага реализуем "ленивое удаление" ("tombstones"), чтобы при простом последовательном переборе ячеек при поиске, когда алгоритм дойдет до этой ячейки, алгоритм не останавливался, если эта пустая ячейка пустая. Если флаг имеет значение 1 (true), то данный слот bin является частью последовательности зондирования, поэтому следует продолжить поиск, если искомый ключ еще не найден.

Флаг `is_empty` имеет значение 1 (true), если слот пуст, поэтому можно поместить в него значение. При вставке хеш-значения при последовательном поиске пустых ячеек можно проверять этот флаг, пока не будет найдена пустая ячейка с искомым индексом ключ или пока не дойдете до пустой ячейки, у которой `in_probe = 0`.

Далее определим структуру самой хеш-таблицы:

```c
struct hash_table 
{
    struct bin *bins;
    unsigned int size;
};
```

Здесь стандартное содержимое - поле-набор ячеек и размер таблицы.

При создании новой таблицы необходимо инициализировать каждую ячейку. Первоначально у ячеек bin не установлен флаг `in_probe`, но поскольку они пусты, установлен флаг `is_empty`:

```c
struct hash_table* new_table(unsigned int size)
{
    struct hash_table *table = malloc(sizeof *table);
    table->size = size;
    table->bins = malloc(size * sizeof *table->bins);

    // инициализация ячеек таблицы начальными значениями
    struct bin empty_bin = {.in_probe = 0, .is_empty = 1};
    for (unsigned int i = 0; i < size; i++) 
    {
        table->bins[i] = empty_bin;
    }
    return table;
}
```

Удаление таблицы стандартно: сначала освобождаем память под ячейки таблицы, а затем структуру самой таблицы:

```c
void free_table(struct hash_table *table)
{
    free(table->bins);
    free(table);
}
```

### Поиск пустых ячеек и ключей

Для вставки хеш-значений (с поиском свободных ячеек) или для поиска нужных хеш-ключей нам потребуется функция зондирования - `p(k, i)`, о которой шла речь в начале темы. Пока определим ее прототип:

```c
unsigned int p(unsigned int key, unsigned int i, unsigned int m);
```

Ее первый аргумент - вставляемое хеш-значение, второй аргумент - индекс для зондирования и последний аргумент - размер хеш-таблицы.

Затем используем эту функцию для написания двух вспомогательных функций. Первая функция будет находить первую пустую ячейку:

```c
struct bin* find_empty(struct hash_table* table, unsigned int key)
{
    // проходим по ячейкам таблицы
    for (unsigned int i = 0; i < table->size; i++) 
    {
        // получаем ячейку по индексу
        struct bin *bin = table->bins + p(key, i, table->size);
        // если ячейка пуста, возвращаем ее
        if (bin->is_empty) return bin;
    }
    // если пустых ячеек нет, пока для простоты возвращаем NULL
    return NULL;
}
```

Другая функция будет искать ячейку, которая заданный хеш-ключ (если он находится в таблице), и при этом эта ячейка не является пустой:

```c
struct bin* find_key(struct hash_table* table, unsigned int key)
{
    // проходим по ячейкам таблицы
    for (unsigned int i = 0; i < table->size; i++) 
    {
        // получаем ячейку по индексу
        struct bin* bin = table->bins + p(key, i, table->size);

        // если хеш равен искомому, а яйчека не используется в зондировании
        // возвращаем данную ячейку
        if (bin->key == key && !bin->is_empty) return bin;
    }
    // иначе возвращаем NULL - индикатор, что ключ не найден
    return NULL;
}
```

### Проверка наличия ключа

Для проверки наличия хеш-ключа в таблице можно использовать функцию `find_key()`. Если она возвращает ячейку с искомым ключом, значит, данный ключ есть в таблице:

```c
int contains_key(struct hash_table* table, unsigned int key)
{
    struct bin *bin = find_key(table, key);
    return bin != 0;
}
```

При этом необходимо проверить и наличие ключа, и пустая ли ячейка, поскольку есть вероятность случайно найти ключ (например, ранее удаленный).

### Удаление

Для удаления ключа можно также использовать функцию `find_key()`:

```c
void delete_key(struct hash_table* table, unsigned int key)
{
    struct bin* bin = find_key(table, key);
    // если нашли ячейку с ключом, делаем ее пустой
    if(bin)
    {
        bin->is_empty = 1;
    }
}
```

Если `find_key()` возвращает ячейку с искомым ключом, то установливаем ее флаг `is_empty` в 1 (true).

### Вставка ключа

Для добавления хеш-ключа в таблицу необходимо выяснить, присутствует ли он уже в таблице - чтобы не вставлять его дважды. Если его нет, то вставить его в первое пустое место. Для первого шага можно использовать `contains_key()`, а для второго - `find_empty()`.

```c
void insert_key(struct hash_table* table, unsigned int key)
{
    if (!contains_key(table, key)) 
    {
        struct bin* bin = find_empty(table, key);
        // если пустые ячейки отсутствуют
        if(!bin)
        {
            printf("Unable to insert the key `%u`. No free bins\n", key);
            return;
        }
        // если нашли пустую ячейку, помещаем в нее данные
        *bin = (struct bin){.in_probe = 1, .is_empty = 0, .key = key};
    }
}
```

Если свободных ячеек больше нет, то в данном случае просто выводим диагностическое сообщение на консоль и выходим из функции.

### Полный пример

Соберем все вместе и посмотрим на примитивном примере:

```c
#include <stdio.h>
#include <stdlib.h>

// ячейка хеш-таблицы
struct bin 
{
    unsigned int key;
    int in_probe : 1;   // является ли частью последовательности зондирования
    int is_empty : 1;   // пустая ли ячейка
};
// структура хеш-таблицы
struct hash_table 
{
    struct bin *bins;
    unsigned int size;
};

// создание хеш-таблицы
struct hash_table* new_table(unsigned int size)
{
    struct hash_table *table = malloc(sizeof *table);
    table->size = size;
    table->bins = malloc(size * sizeof *table->bins);

    // инициализация ячеек таблицы начальными значениями
    struct bin empty_bin = {.in_probe = 0, .is_empty = 1};
    for (unsigned int i = 0; i < size; i++) 
    {
        table->bins[i] = empty_bin;
    }
    return table;
}

// удаление таблицы
void free_table(struct hash_table *table)
{
    free(table->bins);
    free(table);
}
// функция зондирования
// линейное зондирование
unsigned int p(unsigned int key, unsigned int i, unsigned int m)
{
    return (key + i) & (m - 1);
}
// двойное хеширование (double hashing)
unsigned int p2(unsigned int key, unsigned int i, unsigned int m)
{
    unsigned int h1 = key;
    unsigned int h2 = (key << 1) | 1;
    return (h1 + i*h2) & (m - 1);
}

// поиск ячейки с определенным ключом
struct bin* find_key(struct hash_table* table, unsigned int key)
{
    // проходим по ячейкам таблицы
    for (unsigned int i = 0; i < table->size; i++) 
    {
        // получаем ячейку по индексу
        struct bin* bin = table->bins + p(key, i, table->size);

        // если хеш равен искомому, а яйчека не является пустой
        // возвращаем данную ячейку
        if (bin->key == key && !bin->is_empty) return bin;
    }
    // иначе возвращаем NULL - индикатор, что ключ не найден
    return NULL;
}
// поиск пустой ячейки
struct bin* find_empty(struct hash_table* table, unsigned int key)
{
    // проходим по ячейкам таблицы
    for (unsigned int i = 0; i < table->size; i++) 
    {
        // получаем ячейку по индексу
        struct bin *bin = table->bins + p(key, i, table->size);
        // если ячейка пуста, возвращаем ее
        if (bin->is_empty) return bin;
    }
    // если пустых ячеек нет, пока для простоты возвращаем NULL
    return NULL;
}

// проверка наличия ключа 
int contains_key(struct hash_table* table, unsigned int key)
{
    struct bin *bin = find_key(table, key);
    return bin != 0;
}

// удаление ключа
void delete_key(struct hash_table* table, unsigned int key)
{
    struct bin* bin = find_key(table, key);
    // если нашли ячейку с ключом, делаем ее пустой
    if(bin)
    {
        bin->is_empty = 1;
    }
}

// добавление ключа
void insert_key(struct hash_table* table, unsigned int key)
{
    if (!contains_key(table, key)) 
    {
        struct bin* bin = find_empty(table, key);
        // если пустые ячейки отсутствуют
        if(!bin)
        {
            printf("Unable to insert the key `%u`. No free bins\n", key);
            return;
        }
        // если нашли пустую ячейку, помещаем в нее данные
        *bin = (struct bin){.in_probe = 1, .is_empty = 0, .key = key};
    }
}

// получаем хеш-значение из строки
unsigned int hash_fnv1a(const char *str) 
{
   unsigned int hash = 2166136261u;

    while (*str) {
        hash ^= (unsigned char)(*str++);
        hash *= 16777619;
    }

    return hash;
}


// вывод хеш-таблицы
void print_table(struct hash_table* table)
{
    for (unsigned int i = 0; i < table->size; i++) 
    {
        // получаем ячейку по индексу
        struct bin *bin = table->bins + i;
        // просто выводим все ключи из непустых ячеек в строчку
        printf("%u", bin->is_empty?0:bin->key);
        if(i < table->size-1) printf(" - ");
    }
    putchar(10);
}

int main(void)
{
    unsigned int size = 4;
    struct hash_table* dict = new_table(size);
    
    // строки для примера
    char* colors[] = {"red", "green", "blue", "yellow", "black", "white"};
    for(int i =0; i < sizeof(colors)/sizeof(colors[0]); i++)
    {
        // получаем хеш строк
        unsigned int hash = hash_fnv1a(colors[i]);
        // добавляем строки в хеш-таблицу
        insert_key(dict, hash);
    }
    // выводим содержимое
    print_table(dict);

    // получаем хеш строки `red`
    unsigned int red_hash = hash_fnv1a(colors[0]); 

    // проверим, есть ли строка red в таблице
    int is_present = contains_key(dict, red_hash);
    printf("string `red` is %s\n", is_present?  "present" : "absent");

    // удаляем строку `red` из хеш-таблицы
    printf("delete key %u\n", red_hash);
    delete_key(dict, red_hash);

    // снова проверяем, есть ли строка в хеш-таблице
    is_present = contains_key(dict, red_hash);
    printf("string `red` is %s\n", is_present?  "present" : "absent");


    // снова выводим содержимое для проверки
    print_table(dict);

    // удаляем всю хеш-таблицу
    free_table(dict);
    return 0;
}
```

Здесь для примера добавляем несколько ключей. Причем специально пытаемся добавить больше ключей, чем может вместить таблица. Затем выводим таблицу с помощью примитивной функции вывода print_table и затем проверям наличие одной из них в хеш-таблице - до и после удаления. Затем повторно проверяем состояние всей таблицы. В итоге мы получим следующий вывод:

```
Unable to insert the key `1452231588`. No free bins
Unable to insert the key `3724674918`. No free bins

1089765596 - 18738364 - 2197550541 - 96429129

string `red` is present
delete key 1089765596
string `red` is absent

0 - 18738364 - 2197550541 - 96429129
```

### Послесловие

При реализации хеш-таблиц неизбежно возникает вопрос, какую стратегию разрешения коллизий выбрать. Самым простым и, возможно, логичным видится метод цепочек, то есть применение связанных списков. И лучший способ, как всегда, - это тестирование сравниваемых стратегий при реализации конкретной задачи при конкретных условиях. Тем не менее есть несколько аспектов. В частности, поскольку ячейки в таблицах с открытой адресацией размещаются в смежных областях памяти, производительность кэширования, вероятно, будет выше. Если все ячейки помещаются в одну строку кэша, открытая адресация очень эффективна. Но даже если нет, линейное зондирование на небольших хеш-таблицах приведет к меньшему количеству промахов кэша. При линейном зондировании обращение идет к близлежащим областям памяти, что оптимально для эффективности кэширования. При двойном хешировании происходит перемещение по памяти, поэтому следует ожидать большего количества промахов кэша. Хотя при линейном зондировании длина последовательности может быть больше, чем скажем при двойном хешировании или при проходе по связанному списку при методе цепочек, но улучшенная производительность кэша может компенсировать это, особенно когда максимальное количество элементов ограничено размером таблицы.
