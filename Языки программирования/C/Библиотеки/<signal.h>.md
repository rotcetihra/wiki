## Описание

Заголовочный файл `<signal.h>` предоставляет средства обработки аппаратных и программных сигналов. Сигналы — механизм асинхронного уведомления программы о событиях (ошибках, внешних запросах и т. д.). Каждый сигнал имеет обработчик, который определяет реакцию программы.

### Dispositions (Распоряжения)

Каждый сигнал имеет текущее _распоряжение_, которое определяет поведение процесса при его получении:

- **Term** — завершение процесса
- **Ign** — игнорирование сигнала
- **Core** — завершение процесса с дампом памяти
- **Stop** — остановка процесса
- **Cont** — продолжение выполнения, если процесс остановлен

Процесс может изменить распоряжение сигнала с помощью `sigaction(2)` или `signal(2)`. Используя эти системные вызовы, процесс может выбрать одно из следующих поведений при получении сигнала: выполнить действие по умолчанию, игнорировать сигнал или перехватить сигнал обработчиком сигналов — определённой программистом функцией, которая автоматически вызывается при получении сигнала.

По умолчанию обработчик сигналов вызывается на нормальном стеке процесса. Можно организовать использование альтернативного стека; см. `sigaltstack(2)`.

Распоряжение сигнала является атрибутом процесса: в многопоточном приложении распоряжение определённого сигнала одинаково для всех потоков.

Дочерний процесс, созданный через `fork(2)`, наследует копию распоряжений сигналов родителя. Во время `execve(2)` распоряжения обрабатываемых сигналов сбрасываются на значения по умолчанию; распоряжения игнорируемых сигналов остаются без изменений.

### Реалтайм-сигналы

Начиная с Linux 2.2, Linux поддерживает реалтайм-сигналы, как определено в POSIX.1b (теперь включено в POSIX.1-2001). Диапазон поддерживаемых реалтайм-сигналов определяется макросами `SIGRTMIN` и `SIGRTMAX`. POSIX.1-2001 требует, чтобы реализация поддерживала как минимум `_POSIX_RTSIG_MAX` (8) реалтайм-сигналов.

В отличие от стандартных сигналов, реалтайм-сигналы не имеют предопределённых значений: весь набор реалтайм-сигналов может использоваться для целей, определённых приложением.

### Маска сигналов

Каждый поток в процессе имеет независимую _маску сигналов_, которая указывает набор сигналов, которые поток в данный момент блокирует. Поток может манипулировать своей маской сигналов с помощью `pthread_sigmask(3)`. В традиционном однопоточном приложении можно использовать `sigprocmask(2)`.

Дочерний процесс, созданный через `fork(2)`, наследует копию маски сигналов родителя; маска сигналов сохраняется через `execve(2)`.

## Возвращаемое значение

Функции `signal()` возвращают предыдущее значение обработчика для указанного сигнала или `SIG_ERR` при ошибке.

Функция `raise()` возвращает 0 при успехе и ненулевое значение при ошибке.

## Исключения

- **Установление `errno`:** `signal()` устанавливает `errno` при ошибке (но POSIX не гарантирует этого; на Linux не устанавливает). `raise()` не устанавливает `errno`.
- **Поведение при передаче `NULL`:** не применимо — аргументы являются целочисленными значениями сигналов или указателями на функции.
- **Поведение при переполнении/нехватке памяти:** не применимо.
- **Граничные случаи:**
  - Сигналы `SIGKILL` и `SIGSTOP` не могут быть перехвачены, заблокированы или проигнорированы.
  - Автоматические переменные, не объявленные как `volatile sig_atomic_t`, имеют неопределённое значение после возврата из обработчика сигнала.
  - Если функция, вызвавшая `setjmp()`, вернулась до вызова `longjmp()` в обработчике — неопределённое поведение.
- **Многопоточность:** обработчики сигналов являются процессными — распоряжение сигнала одинаково для всех потоков.
- **Асинхронная безопасность:** функции, которые можно безопасно вызывать из обработчика сигналов, перечислены в `signal-safety(7)`. Большинство стандартных функций библиотеки C _не_ являются асинхронно безопасными.
- **Осторожность:** поведение при повторных сигналах (сигнал возникает во время обработки предыдущего) зависит от реализации. На POSIX-системах можно использовать `sigaction` для более тонкой настройки.
