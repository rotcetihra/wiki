# Критическое изменение: Смешанные декларации (Mixed Declarations)

Это изменение — одно из самых значимых для архитектуры Sass за последнее время. Оно напрямую связано с тем, как нативный CSS теперь поддерживает вложенность (CSS Nesting). Чтобы Sass-код не конфликтовал с правилами браузеров, порядок обработки свойств и вложенных правил становится более строгим.

---

## 1. Суть проблемы: Порядок имеет значение

Исторически Sass позволял писать свойства (декларации) в любом месте внутри блока: до, после или вперемешку с вложенными селекторами.

```SCSS
.card {
  color: red;        // Свойство до вложения
  .title { font-size: 2rem; }
  margin: 10px;      // Свойство ПОСЛЕ вложения (Mixed Declaration)
}
```

В старых версиях Sass просто «поднимал» свойство `margin` вверх, и в итоговом CSS оно оказывалось рядом с `color`. Однако в стандартном CSS Nesting свойства, идущие после вложенных правил, ведут себя иначе или могут игнорироваться в зависимости от контекста.

---

## 2. Что изменилось?

Теперь Sass следует правилам нативного CSS. Если вы объявляете свойство **после** вложенного правила, Sass выдает предупреждение. В будущих версиях это приведет к изменению визуального результата, так как свойства после вложенности будут неявно оборачиваться в специальный селектор `& { ... }`.

### Почему это критично?

Это влияет на **специфичность** и **каскад**. Если свойство «обернуто» во вложенность, оно может перекрывать другие свойства иначе, чем если бы оно было обычным свойством родителя.

---

## 3. Рекомендация: Правило «Сначала свойства»

Чтобы избежать путаницы, багов с каскадом и предупреждений компилятора, необходимо придерживаться простого правила: **все свойства элемента должны быть объявлены до любых вложенных правил.**

|**Плохо (Mixed)**|**Хорошо (Clean)**|
|---|---|
|`.btn {`|`.btn {`|
|`padding: 10px;`|`padding: 10px;`|
|`&:hover { color: red; }`|`margin: 5px;`|
|`margin: 5px; // ОШИБКА`|`&:hover { color: red; }`|
|`}`|`}`|

---

## 4. Как это выглядит в скомпилированном CSS

Рассмотрим, как Sass теперь обрабатывает «смешанный» код для совместимости с CSS:

**Исходный Sass:**

```SCSS
.box {
  width: 100px;
  .child { color: blue; }
  height: 100px; // Свойство после вложения
}
```

**Современный вывод (Dart Sass):**

```CSS
.box {
  width: 100px;
}
.box .child {
  color: blue;
}
.box {
  /* Sass может вынести это в отдельный блок или обернуть в & {} */
  height: 100px;
}
```

Это разделение может привести к тому, что `height` применится позже, чем ожидалось, что в сложных проектах ломает логику приоритетов.

---

## 5. Как исправить проект (Миграция)

Если ваш проект насчитывает сотни файлов со смешанными декларациями, ручная правка будет трудоемкой. Для этого случая предусмотрен автоматический мигратор.

**Запуск через Sass Migrator:**

```Bash
npm install -g sass-migrator
sass-migrator mixed-decls --migrate-deps main.scss
```

Инструмент автоматически переместит все свойства в начало блоков, соблюдая правильную иерархию.

---

## 6. Сроки внедрения

- **Dart Sass 1.77.7:** Появились официальные предупреждения о смешанных декларациях.
    
- **Sass 2.0.0:** Порядок обработки изменится окончательно. Свойства после вложенных правил будут иметь другую специфичность, так как будут трактоваться по правилам нативного CSS Nesting.

> [!IMPORTANT]
> 
> Это изменение — не просто каприз разработчиков Sass, а вынужденная мера для того, чтобы ваш скомпилированный код работал в браузерах будущего точно так же, как он работает сейчас. Чистота структуры селекторов теперь стала техническим требованием.
